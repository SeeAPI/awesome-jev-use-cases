# 维护案例集

[English](maintaining.md) · [简体中文](maintaining.zh-CN.md)

## 文件职责

| 可编辑来源 | 维护内容 | 生成结果 |
| --- | --- | --- |
| `content/cases/<stable-id>.md` | 单个项目的固定 ID、分类、双语正文、原始素材与旧锚点 | 完整案例集、首页摘要、检索索引 |
| `content/pages/background.en.md`、`background.zh.md` | 模型背景、接入指南、核查范围与来源说明 | 案例集背景章节 |
| `data/site.json` | 固定分类 ID、双语名称、说明及内容更新日期 | 首页和案例集目录 |
| `data/cases/<stable-id>.json` | 可选的结构化元数据与证据，目前有 12 条 | 聚合数据与兼容案例卡 |
| `data/featured-media.json` | 固定版本的作者素材或实现链接、截图来源及模拟模式标注 | 首页和案例集素材区 |
| `data/search-aliases.json` | 经核查的双语同义词组 | 离线检索行为 |
| `scripts/generate.py` | 首页排版与六个精选配置 | 首页、案例集、索引、案例卡及 `llms.txt` |

读者从首页进入完整案例集。`cases/` 是为保留旧链接而提供的元数据参考页，不是必经阅读步骤。`README_zh.md` 保留为生成的兼容入口。

## 新增或修改案例

1. 修改对应的 `content/cases/<stable-id>.md`。新增时沿用现有结构，填写唯一的小写 ID、来源链接、分类与显示顺序；旧锚点字段设为 `legacy_anchors: {en: [], zh: []}`。
2. 保留 `<!-- case:en -->` 和 `<!-- case:zh -->` 两个区段。在开头或场景与做法字段说明具体问题和 Jev 的作用，用于首页及检索摘要。正文保留实现、证据、限制和原始来源。
3. 相对路径以源文件所在目录为准，例如 `../../assets/...`。生成器会调整首页和案例集中的路径。
4. 不修改已有 ID 和旧锚点。`order` 只影响分类中的显示位置；顺序相同时按固定 ID 排列。显示编号自动生成，不需逐个修改。
5. 只在有证据时补充结构化元数据，其 ID 必须与案例一致。不要为填满字段而推断判断类型或实测结果。
6. 更新 `data/site.json` 的内容日期及更新记录，重新生成并检查两种语言。内容日期不表示全部项目都重新测试过。

不要手工编辑生成的首页、案例集、聚合 JSON 或案例卡。多人协作时先合并独立源文件，再重新生成公共输出；这能减少手工合并，但不能保证 Git 不报告生成文件冲突。

## 检查

使用 Python 3.9 或更高版本：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python scripts/generate.py
.venv/bin/python scripts/validate.py
.venv/bin/python -m unittest discover -s tests -v
```

PR 检查针对提交的生成结果执行验证和测试，不会通过重新生成掩盖过期文件，也不调用模型、同步飞书或发布内容，不需要密钥。

检查覆盖元数据、身份一致性、原文哈希、旧锚点、生成文件和本地链接。测试覆盖案例插入、分类重排、双语检索及路由失败处理。这些检查不证明外部网站仍然可访问，也不证明模型效果。

`data/migration-baseline.json` 记录重构前的正文哈希。拆分文件时没有重写它。明确的内容修正需要只更新相应基线项，并在更新记录和 PR 中说明原因；不要整体重建基线来掩盖遗漏。

## 后续维护

- 分批改善摘要、同义词与元数据。
- 只添加有可复制输入、明确限制及离线检查的配方。
- 取得并核查原始证据后，再发布独立评测。
- 单独衡量流量与来源；目录调整本身不能证明 Star 或流量增长。

首页还会使用已有的可借鉴点或实现模式，以及边界字段的首句。首句应能独立表达含义，完整限制保留在案例集，不为填空而补造结论。
